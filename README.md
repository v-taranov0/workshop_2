# Лабораторная работа: асинхронность в Python на пальцах

## Цель, подготовка и правила

За одну пару (90 минут) вы на простых примерах без HTTP и внешних API разберётесь, что такое корутина, точка переключения и event loop. Работа идёт по мотивам лекции «Асинхронное программирование в Python».

К концу работы вы должны уметь:

- объявить корутину и запустить её через `asyncio.run`;
- объяснить, почему `await` в цикле не даёт ускорения;
- запускать задачи конкурентно через `asyncio.gather` или `asyncio.create_task`;
- увидеть, как один блокирующий вызов замораживает весь event loop, и починить это.

### Подготовка (5 минут)

Нужен Python 3.10 или новее, сторонние библиотеки не требуются.

1. Скопируйте к себе папку `starter`. В ней лежат заготовки для каждого шага и файл `timer.py` с двумя помощниками:
    - `print_time()` — контекстный менеджер, печатает общее время блока;
    - `log(message)` — печатает строку с меткой времени от старта, например `[  0.5s] alice: ответ отправлен`.
2. Проверьте, что всё запускается:

```
cd starter
python step1_sync.py
```

Пока программа выведет только `Time elapsed: 0.00s` — это нормально.

### Правила

- Работайте по шагам. Каждый шаг заканчивается запуском и сверкой вывода с ожидаемым. Не переходите дальше, пока вывод не совпал.
- **Письменные** контрольные вопросы отмечены звёздочкой `*`. Ответы на них записывайте в файл `answers.md` — он сдаётся вместе с кодом. Остальные вопросы обсудим устно в конце пары, но подумать над ними стоит сразу.

## Шаг 4. Блокировка event loop (дополнительно, 20 минут)

Файл: `step4_blocking.py`. В заготовке уже лежит готовый асинхронный сервер из шага 3б, копировать ничего не нужно.

Теперь `bob` прислал не запрос к базе, а задачу на тяжёлые вычисления. В заготовке есть синхронная функция `heavy_compute()`, которая считает 1–3 секунды в зависимости от машины.

### 4а. Ломаем (5 минут)

В `handle_request` для клиента `bob` вызовите `heavy_compute()` вместо `await asyncio.sleep(duration)`. Остальные клиенты по-прежнему ждут через `asyncio.sleep`. Запустите.

Ожидаемый вывод (время `bob` у вас будет своё):

```
[  0.0s] alice: запрос принят
[  0.0s] bob: запрос принят
[  1.4s] bob: ответ отправлен
[  1.4s] carol: запрос принят
[  1.4s] dave: запрос принят
[  1.4s] eve: запрос принят
[  1.4s] alice: ответ отправлен
[  1.9s] carol: ответ отправлен
...
```

Контрольные вопросы:

12. `carol`, `dave` и `eve` не получили даже `запрос принят`, пока считал `bob`. Почему, ведь всё написано на `async`?
13. Где точка переключения в `handle_request`, когда обрабатывается `bob`? Есть ли она вообще?

### 4б. Чиним (10 минут)

Вынесите `heavy_compute` из event loop, чтобы остальные клиенты не ждали `bob`. Два инструмента из лекции:

```python
await asyncio.to_thread(heavy_compute)
```

```python
from concurrent.futures import ProcessPoolExecutor

loop = asyncio.get_running_loop()
await loop.run_in_executor(pool, heavy_compute)
```

Во втором случае `pool` — это `ProcessPoolExecutor()`: откройте его через `with` внутри `main` и передайте в `handle_request` параметром.

Попробуйте оба варианта. Порядок строк должен стать как в шаге 3б: быстрые клиенты отвечают на 0.5 с, `bob` последним. Посекундно вывод не совпадёт — время `bob` зависит от машины.

Контрольные вопросы:

14. Оба инструмента разблокировали event loop, и время у них, скорее всего, совпало. Но `heavy_compute` — CPU-bound, а по лекции потоки для CPU-bound в Python не помогают из-за GIL. Почему поток всё-таки сработал здесь? Подсказка: чем занят event loop, пока `bob` считает в потоке?
15. Куда бы вы вынесли синхронный `requests.get`, если бы он попался в корутине? Почему для него точно достаточно потока?

### 4в. Когда поток перестаёт спасать (5 минут)

Сделайте тяжёлыми трёх клиентов: `bob`, `dave` и `eve`. Запустите оба варианта из 4б и сравните общее время.

Ожидаемый результат: с `to_thread` три вычисления идут по очереди, общее время — около трёх `heavy_compute`. С пулом процессов они идут параллельно, общее время — около одного `heavy_compute`.

16. Почему потоки не дали параллелизма, а процессы дали? Сформулируйте правило: когда для блокирующего вызова хватает потока, а когда нужен процесс.
